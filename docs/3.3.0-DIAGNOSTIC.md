## 1.1 Audio streams

`buildArgs` (src/encoder/pipeline.js:655-703) and `buildFallbackArgs`
(:705-728) emit **no `-map`**. Audio handling is one decision for one stream,
the same in both tiers:

```js
// pipeline.js:689-698
if (audioStream) {
  const aCodec = (audioStream.codec_name || '').toLowerCase();
  if (aCodec.startsWith('pcm_')) args.push('-c:a', 'aac', '-b:a', '320k');
  else args.push('-c:a', 'copy');
} else args.push('-an');
```

`audioStream` is `pickAudioStream` (:367-370), the first audio stream. With no
`-map`, ffmpeg's default stream selection takes one video stream (highest
resolution) and **one** audio stream (most channels). Every other audio track
is dropped silently and ffmpeg exits 0.

Reproduced with the bundled ffmpeg through `scripts/print-args.js` (the app's
own argv):

| Tier | Source streams | Output streams | ffmpeg exit |
|---|---|---|---|
| Make It Fast | video, audio (AAC), audio (AAC) | video, audio | 0 |
| Slow But Better | video, audio (AAC), audio (AAC) | video, audio | 0 |

Same on a real clip: `iphone_prores_hq_IMG_3069.MOV` carries pcm_s32le stereo
plus pcm_f32le 4-channel; today only one survives.

## 1.2 MP4 muxer codec decision table (bundled ffmpeg 8.1.2)

Measured: a 2 s sine in each codec, then `-c copy` into `.mp4` with the bundled
binary. Then a transcode of each to AAC with both `aac_at` and `aac`.

| Codec | `-c copy` into MP4 | Sample entry written | Decision for 3.3.0 |
|---|---|---|---|
| AAC | OK | `mp4a` | **copy** |
| ALAC | OK | `alac` | **copy** |
| AC-3 | OK | `ac-3` | **copy** |
| E-AC-3 | OK | `ec-3` | **copy** |
| PCM s16le / s24le / s32le (also s16be, f32le) | OK | `ipcm` (ISO 23003-5) | **transcode → AAC 320k** (see note) |
| Opus | OK | `Opus` | transcode → AAC 320k |
| FLAC | OK | `fLaC` | transcode → AAC 320k |
| MP3 | OK | `mp4a` (OTI 0x6B) | transcode → AAC 320k |
| DTS | OK | `mp4a` (OTI 0xA9) | transcode → AAC 320k |
| TrueHD | **FAIL**: "truehd in MP4 support is experimental, add '-strict -2'" | — | transcode → AAC 320k |
| MP2 | OK | `mp4a` (OTI 0x6B/0x69) | transcode → AAC 320k |
| Vorbis | OK | `mp4a` (OTI 0xDD) | transcode → AAC 320k |

All 16 inputs transcoded to AAC with both encoders (no failures). PCM is
transcoded, not copied: `-c:a copy` writes `ipcm` without HandBrake's
one-sample-per-packet constraint, which QuickTime needs.

**Drop-with-warning:** after transcoding, the muxer takes every codec the
build can decode. So the only drop case is an audio stream the bundled
ffmpeg cannot decode (ffprobe reports no codec name, or no channels). That
track is dropped with `DROPPED-AUDIO`, and the file still encodes.

### AAC encoder and channel layouts (finding that shapes 1b)

`aac_at` is present (`ffmpeg -encoders`: `A..... aac_at  aac (AudioToolbox)`).
It does **not** always keep the channel count. Measured with 320k per track,
source PCM s24le with each layout:

| Source layout | `aac_at` output | `aac` output |
|---|---|---|
| mono | 1, mono | 1, mono |
| stereo | 2, stereo | 2, stereo |
| 2.1 | **2**, stereo | 3, 2.1 |
| 3.0 | 3, 3.0 | 3, 3.0 |
| 4.0 / quad | 4, 4.0 / quad | 4, 4.0 / quad |
| 4.1 | **6**, 5.1 | 5, unknown |
| 5.0 / 5.0(side) | 5, 5.0 | 5, 5.0 / unknown |
| 5.1 / 5.1(side) | 6, 5.1 | 6, 5.1 / unknown |
| 6.0 | 6, hexagonal | 6, unknown |
| 6.1 / 6.1(back) | 7, 6.1(back) | 7, unknown |
| 7.0 | 7, unknown | 7, unknown |
| 7.1 | **7**, unknown | 8, 7.1 |
| 7.1(wide) | 8, 7.1 | 8, unknown |
| octagonal | 8, unknown | 8, unknown |
| 4-ch, no layout (iPhone ProRes 2nd track) | 4, 4.0 | 4, 4.0 |

`aac_at` changes the channel count on 2.1, 4.1 and 7.1. The built-in `aac`
always keeps the count, but cannot label unusual layouts in MP4 and writes them
as "unknown". Implementation consequence: use `aac_at` when its output is known
to match the source (mono, stereo, 3.0, 4.0, quad, 5.0, 5.0(side), 5.1,
5.1(side), 6.1(back); or a layout-less track of 1, 2, 4 or 6 channels).
Otherwise use the built-in `aac`, which keeps the channel count. `aac_at` caps
mono at about 260 kb/s.

## 1.3 Timecode into .mp4

Synthetic MOV: HEVC + PCM + `tmcd` at `01:00:00:00` (video stream also tagged
`timecode=01:00:00:00`). Output always `.mp4`, both re-encoded. ffprobe of each
output:

| Combination | video `timecode` tag | `tmcd` track in output | format `timecode` tag |
|---|---|---|---|
| A `-map_metadata 0 -movflags use_metadata_tags+faststart` (today) | 01:00:00:00 | yes | — |
| B A + `-dn` | 01:00:00:00 | yes | — |
| C A + `-write_tmcd 1` | 01:00:00:00 | yes | — |
| D C + `-dn` | 01:00:00:00 | yes | — |
| E `-timecode 01:00:00:00` | 01:00:00:00 | yes | 01:00:00:00 |
| F E + `-dn` | 01:00:00:00 | yes | 01:00:00:00 |
| H `-map_metadata 0 -timecode … -dn` | 01:00:00:00 | yes | 01:00:00:00 |
| J `-timecode … -write_tmcd 0` | — | **no** | 01:00:00:00 |

The MP4 muxer writes a `tmcd` track from the **output video stream's
`timecode` tag** (`write_tmcd` auto). `-dn` does not conflict, because the
muxer synthesises the tmcd track rather than mapping the source data stream.

On real clips, today's argv carries timecode only when it sits on the video
stream:

| Clip | Where the source timecode lives | Today's output |
|---|---|---|
| `iphone16pro_hevc422_4k60_IMG_0311.mov` | video tag + `tmcd` 17:09:16:08 | carried (tag + tmcd) |
| `prores_proxy_s24.mov` | video tag + `tmcd` 00:00:00:00 | carried |
| `sony_xavc_420_C0024.MP4` (and C0819, C0817) | only on the `rtmd` data stream (10:14:17:14) | **lost** |

**Working combination for 3.3.0:** explicit `-timecode <source tc>` taken from
the first `timecode` tag found (video stream, else any stream, else format),
with explicit `-map` for video + audio (so no data or subtitle stream is ever
mapped; equivalent to `-sn -dn`). Proven on rows E/F/H: it writes the tag and
the tmcd track for every source location, including Sony's `rtmd`.

## 1.4 pickVideoStream

```js
// pipeline.js:355-365
for (const s of streams) {
  if (s.codec_type !== 'video') continue;
  if (s.disposition && s.disposition.attached_pic === 1) continue;
  const c = (s.codec_name || '').toLowerCase();
  if (c === 'mjpeg' || c === 'png' || c === 'gif' || c === 'bmp') continue;   // ← rejects MJPEG video
  return s;
}
```

The `attached_pic` check comes first, so cover art is already skipped. The
codec-name line then also rejects genuine MJPEG video (old cameras, webcams,
some DSLRs), and the file is ignored as non-video. Fix (HandBrake's rule): the
first video stream that is not `attached_pic` and has a decoder in the bundled
build, with no codec-name rejection. The stream index must also flow into
`-map`, because today's argv never says which stream to encode. With
cover-art-first files, ffmpeg's default "highest resolution" pick can choose
the cover.

## 1.6 HDR chip

Detection: `detectDroppedHdrMeta` (pipeline.js:624-639) labels **any**
Mastering display, Content light, or DOVI side data as dropped. runBatch logs
`HDR-METADATA … re-encoding does not carry this metadata` (:1131-1135) and
sends `hdrMeta` on file-done. The renderer shows an "HDR" chip whose tooltip
says the metadata "re-encoding doesn't keep" (renderer.js:1863-1872), plus a
run-summary note (renderer.js:2525-2535).

Measured on outputs of today's argv (bundled ffmpeg; ffprobe stream + frame
side data, plus an MP4 box walk for `colr` / `mdcv` / `clli` / `dvcC` / `dvvC`):

| Source → output | mastering display | content light | DV config record (dvcC/dvvC) | DV RPU (per-frame) | `colr` atom |
|---|---|---|---|---|---|
| HDR10 synthetic (PQ, MDCV + CLL SEI) → Make It Fast | **carried** (`mdcv` box + SEI) | **carried** (`clli` box + SEI) | n/a | n/a | written |
| HDR10 synthetic → Slow But Better | **carried** (`mdcv` + SEI) | **carried** (`clli` + SEI) | n/a | n/a | written |
| iPhone 12 HLG + Dolby Vision 8.4 (`IMG_2461`, source has `dvvC`, RPU on every frame, no MDCV/CLL) → Make It Fast | — (none in source) | — | **dropped** | **carried** (Dolby Vision RPU Data on every decoded frame) | written |
| same → Slow But Better | — | — | **dropped** | **dropped** | written |

So today's chip is wrong for HDR10: it claims mastering display and content
light are dropped when both tiers carry them. For Dolby Vision, the truth is
that the configuration record is dropped in both tiers, and the per-frame data
is dropped in Slow But Better only. (Ambient viewing environment is carried in
both tiers.)
