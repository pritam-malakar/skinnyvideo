### Item 1: recovery can flatten the wrong folder (HIGH): **done**

Reproduced first, with the auditor's layout, in `test/recover_run_dir_test.js` on `399c3d2`:
Keep on a complete recorded leftover at
`Compressed_archives/Output/Compressed_2026-10-20_0101/Selected files (1)/Card/clip.tmp.mp4`
took `Compressed_archives` (first ancestor whose name starts with `Compressed_`) as the run
folder and flattened it. The regression came in with `1c93bbe` (F2, `flattenRunDir` on Keep).

What changed:
* `src/encoder/naming.js`: one predicate, `isRunFolderName(name)` =
  `/^Compressed_\d{4}-\d{2}-\d{2}_\d{4}$/`. Used by the scanner's run-folder exclusion
  (`pipeline.walkAll`, which had its own copy of the regex), `flattenRunDir` (refuses any
  folder whose name fails it), and `orphans.isDeletablePartial` (was a `/Compressed_`
  substring match). Grep for `Compressed_`: the remaining hits are `tsRunFolder` (which
  makes the name), comments, and a log line.
* The exact run folder is recorded with each partial when it is created:
  `pipeline` → `onPartial(tmp, { final, source, runDir })` → main stores it in
  `prefs.partialInfo[tmp].runDir`.
* `orphans.classifyPartials` / `recoverPartials` use only that recorded folder, and never
  walk ancestors. If the record has no `runDir`, the folder is gone or is not a directory,
  its name fails the predicate, or the partial is not inside it, the leftover is
  incomplete (the launch prompt offers Delete only) and
  `RECOVER-SKIP <path> (run folder not found)` is logged (app console via `console.log`:
  the run folder is the only place a compress.log could go, and it is the thing missing).

Tests:

  everything outside the run folder (path, size, mtime) identical before/after, flat run

### Item 3: retry and software fallback bypass the pause gate (MEDIUM): **done**

Reproduced first in `test/attempt_pause_gate_test.js` on `399c3d2`: with the pause landing
right after the primary encoder exited, the colour-tag-free retry (and in the other cases the
libx265 fallback) spawned and finished while the batch was paused.

What changed:
* `src/encoder/pipeline.js`: one `attemptGate(fileBoundary)` inside `runBatch`, called
  right before **every** encode spawn (primary, colour-tag-free retry, libx265 fallback).
  It waits on the pause gate, then returns `'cancel'` if cancelled; `'stop'` only at the
  file boundary (the primary), so a stop still lets the current file finish, retry and
  fallback included. A cancel between attempts spawns nothing; the existing cancel branch
  logs `CANCELLED <file> (operator cancel — no-color retry|fallback encoder not started)`.
* `src/main/queue-runner.js` `requestStop`: a stop now clears `paused` even when no child
  is alive (paused between two attempts), and reports the batch Running again. Before,
  the flag stayed set, so the retry the stop lets through would have run while the row
  still read "Paused", with the stall watchdog off (it treats a paused batch as alive).

Tests: `test/attempt_pause_gate_test.js` (new, 24 checks; scripted fake ffmpeg child, no

### Item 2: overlapping scans can queue the wrong files (MEDIUM): **done**

Reproduced first in `test/scan_race_test.js` on `399c3d2`: pick folder `first` (slow scan),
then folder `second` (fast scan). `first`'s late result passed the stale check (it compared
the shared `current` object, which both picks share) and replaced `second`'s files, while the
batch name still said `second`.

What changed (`src/renderer/renderer.js`): every pick (drop or Browse, folder or files) takes a
unique id from a counter in `stagePicked`, stored on the staging slot (`current.scanId`). A
response writes the slot only while its id is still the slot's latest (`isLatestScan`), in
`stagePicked` after `stat-path`, and in `stageSource` / `stageFiles` after the scan and in
their error paths. The id stays in the renderer: main's scan handlers are unchanged, since
only the renderer decides which response wins.

Dry-run preview: no separate race. It is not a renderer-side request; a Preview batch runs in
main as a queued batch and reports through `progress` events keyed by batch id. Nothing to
change there.

Tests: `test/scan_race_test.js` (new, Electron, 4 checks; real renderer + preload, main's
scan handlers stubbed with set delays): FOLDERS, FILES (two file-list picks), STAT (the first
pick still in its `stat-path` call when the second is scanned), ADD-RESET (guard: a scan

### Item 5: `.tmp.mp4` excluded by filename everywhere (MEDIUM): **done**

Reproduced first in `test/tmp_name_scan_test.js` on `399c3d2`: a real `holiday.tmp.mp4`
next to `beach.mov` in an ordinary folder was left out of the scan and counted as
"skipped inside SkinnyVideo output folders".

What changed:
* `src/encoder/pipeline.js` `walkAll` no longer matches any file name. A video is left out of
  a folder scan only when (a) it is inside a folder that passes `isRunFolderName` (Item 1's
  predicate; the whole run folder is skipped and its videos counted, as before), or (b) its
  path is one of the partials main has recorded. `TEMP_OUTPUT_RE` is gone. `scanFolder(src,
  { keepAll, partials })` takes the recorded paths; staged file-list batches (`keepAll`,
  explicit picks) are never filtered, as before.
* The recorded set reaches every scan: main's `scan-source` and `scan-files` handlers pass
  `prefs.pendingPartials`; `runQueue` gets `recordedPartials()` and stores it on the batch at
  its turn (`batch.recordedPartials`, next to `batch.skip`), which `runBatch` and
  `dryRunBatch` pass to `scanFolder`.
* The staging line's "· N skipped inside SkinnyVideo output folders" and the run log's
  `SKIPPED_OUTPUTS` line are unchanged and count both kinds.

### Item 4: reordering queued batches during a run doesn't change execution order (MEDIUM): **done, live reorder**

Reproduced first in `test/live_reorder_test.js` on `399c3d2`: three queued folder batches
A, B, C; Start; while A ran, a real drop of C's row onto B's row. The queue showed A, C, B;
main ran A → B → C.

**Path chosen: live reorder.** Per the decision rule I read `src/main/queue-runner.js`. The
runner already picks the next batch at each batch boundary from a live list: `runQueue`
loops `for (let i = 0; i < batches.length; i++) { … const batch = batches[i]; … }` over the
same array main's `enqueue-batch` handler appends mid-run drops to (`liveBatches`), with the
comment "Do NOT cache `batches.length`". `batches[i]` is read at each turn, so reordering the
not-yet-started part of that array is enough; the loop itself is unchanged. Dragging is not
disabled, and nothing went to BLOCKED.

What changed:
* `src/main/queue-runner.js`: the loop marks `rt(id).started` when it takes a batch.
  New `reorderPending(batches, ids, rt)` reorders only batches not yet started, within the
  slots they already occupy (so the loop's index stays valid); ids not listed keep their
  relative order after the listed ones; unknown ids are ignored.
* `src/main/main.js`: `reorder-batches` IPC handler (validates a list of positive integer
  ids; applies only while a run is live, since before Start the Start payload already
  carries the renderer's order).
* `src/main/preload.js`: `reorderBatches(ids)`.
* `src/renderer/renderer.js`: on every drop during a run, sends the queued batches' new order.
  Rules for what can be dragged are unchanged: only queued batches, only onto queued batches.
* `test/sandbox_ipc_test.js`: one more bridge call (`reorderBatches`) in its list of real
  calls (28 calls, was 27; the bridge-surface check compares against preload.js, so it
  covers the new function automatically).

Tests: `test/live_reorder_test.js` (new, Electron, 6 checks; REAL main.js + preload +
renderer + queue-runner + pipeline, only the native folder dialog stubbed, ffmpeg/ffprobe a
scripted fake child, temp userData with `autoUpdateCheck: false`): `reorderPending` unit
check; LIVE (A running when the drop lands; shown A, C, B; executed A → C → B; displayed
