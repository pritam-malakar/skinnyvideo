### Item 1: recovery can flatten the wrong folder (HIGH): **done**

Reproduced first, with the auditor's layout, in `test/recover_run_dir_test.js` on `399c3d2`:
Keep on a complete recorded leftover at
`Compressed_archives/Output/Compressed_2026-10-20_0101/Selected files (1)/Card/clip.tmp.mp4`
took `Compressed_archives` (first ancestor whose name starts with `Compressed_`) as the run
folder and flattened it. The regression came in with `1c93bbe` (F2, `flattenRunDir` on Keep).

What changed:
* `src/encoder/naming.js`: one predicate, `isRunFolderName(name)` =
  `/^Compressed_\d{4}-\d{2}-\d{2}_\d{4}$/`. Used by the scanner's run-folder exclusion
  (`pipeline.walkAll`, which had its own copy of the regex), `flattenRunDir` (refuses any
  folder whose name fails it), and `orphans.isDeletablePartial` (was a `/Compressed_`
  substring match). Grep for `Compressed_`: the remaining hits are `tsRunFolder` (which
  makes the name), comments, and a log line.
* The exact run folder is recorded with each partial when it is created:
  `pipeline` → `onPartial(tmp, { final, source, runDir })` → main stores it in
  `prefs.partialInfo[tmp].runDir`.
* `orphans.classifyPartials` / `recoverPartials` use only that recorded folder, and never
  walk ancestors. If the record has no `runDir`, the folder is gone or is not a directory,
  its name fails the predicate, or the partial is not inside it, the leftover is
  incomplete (the launch prompt offers Delete only) and
  `RECOVER-SKIP <path> (run folder not found)` is logged (app console via `console.log`:
  the run folder is the only place a compress.log could go, and it is the thing missing).

Tests:
* `test/recover_run_dir_test.js` (new, 12 checks): PREDICATE; AUDIT (Keep → `clip.mp4`
  directly in `Compressed_2026-10-20_0101/`, `notes.txt` untouched, full tree snapshot of
  everything outside the run folder (path, size, mtime) identical before/after, flat run
  folder, `RECOVERED` line in that run folder's log); NO-RUNDIR (recorded run folder not on
  disk, and a 3.3.0-style record with no `runDir` → incomplete, RECOVER-SKIP logged, Keep

### Item 3: retry and software fallback bypass the pause gate (MEDIUM): **done**

Reproduced first in `test/attempt_pause_gate_test.js` on `399c3d2`: with the pause landing
right after the primary encoder exited, the colour-tag-free retry (and in the other cases the
libx265 fallback) spawned and finished while the batch was paused.

What changed:
* `src/encoder/pipeline.js`: one `attemptGate(fileBoundary)` inside `runBatch`, called
  right before **every** encode spawn (primary, colour-tag-free retry, libx265 fallback).
  It waits on the pause gate, then returns `'cancel'` if cancelled; `'stop'` only at the
  file boundary (the primary), so a stop still lets the current file finish, retry and
  fallback included. A cancel between attempts spawns nothing; the existing cancel branch
  logs `CANCELLED <file> (operator cancel — no-color retry|fallback encoder not started)`.
* `src/main/queue-runner.js` `requestStop`: a stop now clears `paused` even when no child
  is alive (paused between two attempts), and reports the batch Running again. Before,
  the flag stayed set, so the retry the stop lets through would have run while the row
  still read "Paused", with the stall watchdog off (it treats a paused batch as alive).

Tests: `test/attempt_pause_gate_test.js` (new, 24 checks; scripted fake ffmpeg child, no
VideoToolbox needed, skips only if the bundled ffmpeg is missing). RETRY (primary exits with
"Error applying encoder options"; pause; no spawn for 800 ms; resume; the retry spawns after
the resume, unpaused; no signal sent to any child; PRIMARY-FAIL → RETRY-OK, file ok),
FALLBACK (retry also fails; pause; fallback waits for resume), PLAIN (plain primary failure →
fallback waits), CANCEL (cancel while paused between attempts: no further spawn, file
cancelled, no output), STOP (stop while paused between attempts: the retry still runs,
unpaused; file 1 ok; file 2 never starts; batch ends Stopped).
